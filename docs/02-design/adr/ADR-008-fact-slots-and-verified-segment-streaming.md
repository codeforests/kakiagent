# ADR-008: Fact slots and verified-segment streaming (AGT-02 with streaming)

**Status:** Proposed (awaiting product-owner sign-off)
**Date:** 2026-10-19
**Requirements addressed:** AGT-02, AGT-01, AGT-11, CHN-02, KB-06, KB-15, KB-16, INB-03, APR-01, APR-02, NFR-01, NFR-10, GOV-01, UC-20 (flows 6, 6a, 6b)

**Context**
AGT-02 requires that prices, stock, dates and policies in a reply match a structured KB entity exactly, that the check runs before any part of the reply reaches the visitor, and that "no unverified price, stock, date or policy value is ever displayed, even briefly during streaming". CHN-02 requires streamed replies, and NFR-01 requires first token p95 ≤ 3 s and full reply p95 ≤ 8 s. Checking a whole reply after generation is safe but kills streaming; streaming raw tokens is fast but unsafe. Language models also paraphrase numbers ("about fifty bucks"), convert GST, and do arithmetic, all of which make "exact match" checks fragile.

**Decision**
1. **Protected values are never written by the model; they are rendered from the KB.** Each retrieved approved fact is given to the model with its value **and** a slot token, for example `[[f:9c1e.price]]`, `[[f:9c1e.validity_end]]`, `[[p:hours.sat]]`. The system prompt requires slot tokens for every price, stock level, date, time, duration, percentage and policy term. The **renderer** replaces each slot with the KB value, formatted for SGD and SGT, and applies the GST rule (KB-15: GST-inclusive for GST-registered tenants, with the exclusive amount shown alongside only if needed). A slot that names a fact not in this turn's retrieved, approved, conflict-free set fails verification.
2. **A deterministic verifier checks every segment before release.** After rendering, it scans the text for protected-value patterns: currency amounts in any form (S$, $, SGD, 元, "50 dollars", "fifty bucks"), bare numbers next to price or stock words, percentages, dates and times in EN/ZH formats, durations, and policy trigger phrases (refund, deliver by, guarantee, warranty). Every hit must come from a slot rendering. The only literal numbers allowed are ones that appear verbatim in the visitor's own messages (for example, "200 cupcakes") or in the tenant's display texts (phone number, address). Any other literal protected value fails the segment.
3. **Boundary rules are checked on the same segments:** forbidden commitments and discount language (APR-01) are matched by a rule set plus a Haiku classifier on the triage path. A commitment that needs approval must go through the `draft_approval` tool (APR-02) and is never streamed.
4. **Verified-segment streaming.** Model tokens go into a hold-back buffer in the agent worker. A segment is released to the channel only when it is complete (sentence end, line break, or 160 characters at a word boundary with no open slot token), rendered, and has passed steps 2–3. Visitors therefore see text a sentence at a time, typically starting 0.8–1.5 s after the model's first token. A partial slot (`[[f:9c…`) always holds the buffer.
5. **On failure:** the failing segment is discarded and never sent. The agent makes one regeneration attempt that continues from the already-released prefix, with a system note naming the violation. If that also fails, the turn ends with the tenant's "let me confirm that with the team" text and an escalation (UC-20 6a). Every failure is recorded in the audit log as a guardrail result (GOV-01) and counted for the evaluation dashboards.
6. **System-owned text is rendered, not generated.** The AI disclosure (AGT-11) is prepended by the renderer to the first message of every conversation from the tenant's editable text (empty text is rejected at save time). Next-opening times and SLA times (AGT-09, APR-04) are system slots (`[[sys:next_open]]`), and locale formatting for SGD, SGT and SG phone numbers happens in the renderer (NFR-10).
7. **The same pipeline serves every channel and AI-suggested staff replies (INB-03).** Non-streaming channels (email, Telegram, Meta) send the fully verified message as one unit. Text typed by staff is not blocked, but the inbox highlights any literal price that does not match the KB before sending.

**Options considered**
- **Slots + deterministic segment verifier (chosen)** — protected values come from the database by construction, so "exact match" is exact; the verifier is plain code, fast and testable to 100%. Con: the model must learn slot discipline (prompted and covered by ≥ 50 price cases in AGT-14), and rich arithmetic (totals) is not allowed in streamed text; totals go into `draft_approval` quotes, which are computed in code.
- **Generate the full reply, verify, then fake-stream it** — simplest safe option. Lost: first visible text arrives only after the whole reply is generated (often 4–6 s), threatening NFR-01's first-token p95 ≤ 3 s.
- **Stream raw tokens and retract on failure** — fastest. Lost: AGT-02 explicitly forbids showing an unverified value "even briefly".
- **LLM-as-judge verifier per segment** — handles paraphrase. Lost: adds latency and cost per segment and is not deterministic enough to promise "zero invented prices".

**Consequences**
Streaming granularity becomes sentence-level rather than token-level, which is acceptable in a chat widget and still gives early feedback. "First token" in NFR-01 is measured as the first verified segment leaving the server (see Open issues in architecture.md). The slot vocabulary and the verifier's pattern set become core, versioned packages with their own unit tests and the AGT-14 price subset. Revisit if the evaluation set shows that slot discipline lowers answer naturalness below what the pilot accepts.
