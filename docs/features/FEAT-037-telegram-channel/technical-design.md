# Technical design: FEAT-037 — Telegram channel

> Implements: CHN-05, LED-04 (p: Telegram alerts; web push with FEAT-048), DSH-09 (p: the Telegram channel in each member's preferences), CHN-12 (p: Telegram token revocation detected by the health job and on send; the degraded-channel alert to Owners and Admins by email and Telegram), NFR-17 (p: Telegram inbound is stored before the webhook answers, outbound retried for 24 hours, then shown to staff as failed), CHN-01 (p: the generic webhook route `/hooks/:kind/:connectionId`) · Realizes: UC-25 steps 1–4, 3a, 4a (Telegram) · Screens: SCR-APP-039 (new), SCR-APP-056 (p: the Telegram column and link), SCR-APP-036 (p: the Connect entry), SCR-APP-014 (p: Telegram conversations) (see [ui-design.md](ui-design.md)) · Module: `channels`, `inbox`, `platform` (notifications), architecture §5.2, ADR-005, ADR-008, ADR-011, ADR-012, ADR-013, ADR-014, ADR-015, ADR-019
> Status: designed · 2026-11-09

## 1. Intent

An Owner or Admin creates a bot with Telegram's @BotFather, pastes its token on the Telegram page, and the bot answers customers who message it privately, from the knowledge base, through the same agent, gate and inbox as the widget and email. Messages in group chats are never answered: the bot says once that it only works in private chats and leaves the group. Staff see Telegram conversations in the inbox and reply there; their replies go out through the bot. A revoked or replaced token is detected within 15 minutes, the channel shows as degraded, and Owners and Admins are alerted. Separately, every member can link their own Telegram account to the same bot with one tap, and then gets their alerts (escalations, approvals, hot leads, withdrawn consent, a channel that stops working) on Telegram as well as by email, with the same per-event switches and quiet hours (LED-04, DSH-09).

## 2. Codebase context

- **Channels** (FEAT-034, FEAT-036): `adapter.ts` (`ChannelAdapter`, `IgnoreReason`, `SendResult`), `registry.ts` (`CHANNEL_REGISTRY` has widget and email; `withAdapter` binds a role's ports), `connections.ts` (`setChannelState`, `recordHealth` (audits the degraded/recovered transition, alerts nobody yet), `reportSendFailure`, `runChannelHealth` every 5 minutes, `checkChannelNow`), `channel_connections` already has `credential_ciphertext`/`credential_key_ref` (sealed with `@kaki/platform/secrets`, never used yet) and `ai_reply_cap`. `shape.ts` adds the disclosure, notice and a GOV-14 footer to **every** message. `deliver.ts` `deliverMessage` with `ChannelSender` per conversation channel; the `messages_channel_delivery` trigger creates the delivery and `channel-send` outbox row for every non-visitor message in a non-widget conversation, so staff, agent, notice and approval writers need no change (FEAT-036 D2).
- **Email receive** (`email/receive.ts`) is the inbound pattern: `EmailInboxPort` (inbox functions passed in by the worker), `inbound_events` for idempotency and ignored counts (its `ignore_reason` check lists the email reasons only), contact by address (`contactFor` writes `contacts` directly), reopen within 7 days.
- **No webhook route exists**: ADR-011's `/hooks/:kind/:connectionId` arrives with this feature. The api's widget routes (`app.ts`) show the visitor-zone pattern.
- **Notifications** (FEAT-052): `notify(tx, …)` writes one `notifications` row per recipient (email only); `send.ts` `sendDueNotifications` (scheduler, identity zone) applies `notification_prefs.email_muted` and quiet hours, holds and digests; `kinds.ts` `CHANNELS = ['email']`; contracts `NotificationChannel = ['email']`, `EventPref { event, email }`, `NotificationPrefs.channels`, `sendTo.email` (comments already say "FEAT-037 adds `telegram`"). `NotificationPrefsBody.events.max(AlertEvent.options.length)` widens on its own (FEAT-051 lesson).
- **Contacts** (FEAT-049): unique by email and phone; no other identifier. CHN-08 verified merge is FEAT-039.

## 3. API contracts (`packages/contracts/src/index.ts`)

Widened: `ConversationChannel` + `telegram`; `MessageDelivery.failedReason` + `blocked`; `ContextSidebar.contact` gains `telegramUsername: string | null`; `AlertEvent` + `channel_degraded` (listed only for members with `settings.manage`, FEAT-052 D9); `NotificationChannel` + `telegram`; `EventPref` gains `telegram: z.boolean().optional()` (absent = unchanged); `NotificationPrefs.sendTo` gains `telegram: TelegramAlertLink | null` (null: the business has no bot connected, so the page shows no Telegram column); `TestAlertResult` gains `telegram: z.boolean()` (whether the test also went to Telegram).

```ts
// ---- Dashboard API: Telegram channel (CHN-05, CHN-12; FEAT-037 §3)
TelegramToken = z.string().trim().regex(/^\d{5,16}:[A-Za-z0-9_-]{30,64}$/)   // 422 invalid_format
TelegramChannelResponse = {
  connected: boolean,                               // false → "Connect a bot"
  connection: { id: uuid, state: 'live' | 'offline', health: ChannelHealth, healthReason: ChannelHealthReason | null, version: int } | null,
  bot: { id: string, username: string, name: string, link: string } | null,   // link = https://t.me/<username>
  lastReceivedAt: iso | null,                       // last accepted private message
  ignored: { reason: TelegramIgnoreReason, count: int }[],   // last 7 days
  alertMembers: int,                                // members who linked Telegram for alerts
  settingsVersion: int,
}
TelegramIgnoreReason = z.enum(['group', 'unsupported', 'staff_chat'])
TelegramConnectBody = { token: TelegramToken }
TelegramReplaceBody = { token: TelegramToken, settingsVersion: int }
TelegramDisconnectBody = { settingsVersion: int }
TelegramAlertLink = { state: z.enum(['not_linked', 'pending', 'linked']), name: z.string().nullable(), linkedAt: iso.nullable() }
TelegramLinkStart = { url: z.url(), expiresAt: iso }   // https://t.me/<bot>?start=<code>
```

Routes (`apps/api/src/telegram-channel.ts`, `registerTelegramChannelRoutes`; `settings.manage` (Owner, Admin) unless noted; tenant from the session):
- `GET /api/v1/channels/telegram` → `TelegramChannelResponse`.
- `POST /api/v1/channels/telegram` `TelegramConnectBody` → 201: `getMe` checks the token, the connection is created offline with mode `hidden` (D4), the webhook is registered; 422 `invalid_format`, 422 `token_rejected` (Telegram said 401/404), 409 `already_connected`, 409 `bot_in_use` (the bot is connected to another business), 502 `provider_unavailable`.
- `PUT /api/v1/channels/telegram/token` `TelegramReplaceBody` → 200: a new token for the **same** bot (BotFather `/revoke` gives one), re-registers the webhook and re-checks health at once; 422 `different_bot` (D6), the `POST` errors, 409 `stale`.
- `DELETE /api/v1/channels/telegram` `TelegramDisconnectBody` → 200: `deleteWebhook` (best effort), credential and settings cleared, channel offline, members' alert links deleted; conversations stay in the inbox; 409 `stale`.
- `POST /api/v1/me/notifications/telegram/link` (every member) → 201 `TelegramLinkStart` (a new code replaces an older one; 15 minutes); 409 `no_bot`.
- `DELETE /api/v1/me/notifications/telegram` (every member) → 204: unlinks; the bot says "Alerts stopped" in that chat.
- `POST /hooks/telegram/:connectionId` (public, rate-limited per connection) → 200 once the update is stored or ignored; 401 when `X-Telegram-Bot-Api-Secret-Token` doesn't match; 404 an unknown connection; 5xx leaves Telegram to redeliver (NFR-17). The route is generic (`/hooks/:kind/:connectionId`, ADR-011): the registry entry's `hook` names the handler; a kind without one is 404.

## 4. Schema changes (migration `0054_telegram_channel.sql`)

Dashboard: SELECT, INSERT, UPDATE, DELETE; visitor zone: SELECT, UPDATE `last_received_at`.
- **`telegram_chats`** (customer chats): `(tenant_id, chat_id bigint)` PK, `contact_id`, `conversation_id` (the latest), `last_inbound_at`, `blocked_at` (the customer blocked the bot). Visitor zone reads and writes; dashboard reads.

Dashboard: the member's own row (policy `user_id = app.user_id` in addition to the tenant policy); visitor zone: SELECT, UPDATE (the webhook links and unlinks); identity zone: none (D9).
- `contacts`: `telegram_id bigint`, `telegram_username text` (≤ 32), unique `(tenant_id, telegram_id) where telegram_id is not null` (D5).
- `notifications.channel text not null default 'email'` (check `email | telegram`), `notifications_dedupe_uq` → `(tenant_id, user_id, channel, dedupe_key)`, `skip_reason` + `no_channel`; `notification_prefs.telegram_muted text[] not null default '{}'`.
- **Function** `channel_hook_route(connection uuid, kind text)` → `(tenant_id, secret_hash)` (SECURITY DEFINER, owner NOLOGIN `kaki_channel_hooks`): the webhook has no tenant context until it knows the connection, as `email_route()` (0053).
- New tables: forced RLS, tenant policy, `TENANT_SCOPED_TABLES`, a case each in `rls.int.test.ts`. Seed: none (E2E connects a fixture bot).

## 5. Component design

### 5.1 The Telegram adapter (`packages/channels/src/telegram/`)

- `api.ts`: a minimal Bot API client over `fetch` (no SDK): `getMe`, `setWebhook({ url, secret_token, allowed_updates: ['message', 'my_chat_member'], max_connections: 10 })`, `deleteWebhook`, `getWebhookInfo`, `sendMessage({ chat_id, text, link_preview_options: { is_disabled: true } })` (plain text, no `parse_mode`, so nothing needs escaping), `leaveChat`. Base URL `TELEGRAM_API_BASE` (default `https://api.telegram.org`; the local fake in dev and E2E, §5.6). Errors map to `SendResult`: 401/404 on the token → `auth`; 403 "bot was blocked by the user" → `permanent` with `blocked` (never `auth`: one customer blocking the bot isn't a revoked token); 400 "chat not found" → `permanent`; 429 (`retry_after`) and 5xx/network → `transient`. The token appears only in the request path inside this file and is never logged (the logger's redaction gets `/bot<token>/`).
- `parse.ts` (pure): a Telegram `Update` (Zod, only the fields used) → `InboundEvent` with `externalUserId` = `from.id`, `text` = `text` or `caption` (≤ 4,000, "[…]"), `localeHint` = `from.language_code`, `extensions.telegram = { chatId, chatType, updateId, username, firstName, lastName, command, startPayload, memberStatus }`.
- `ignore.ts` (pure, CHN-05): `group` for `chat.type` `group`, `supergroup` or `channel`; `unsupported` for a private message with no text or caption (sticker, voice, location, contact, photo without caption); edited messages never arrive (`allowed_updates`). `my_chat_member` updates: added to a group → `group`; the customer blocked the bot (`kicked` in a private chat) → `blocked_at`.
- `threadKey` = the private chat ID. `checkHealth`: `getMe` 401/404 → `credential_revoked`; `getWebhookInfo.url` isn't our hook URL → `credential_invalid` (someone pointed the bot elsewhere; we never take it back on our own, D6); network → `unreachable` (two in a row degrade, FEAT-034).
- `send(msg, ctx)` → `sendMessage` to `ctx.threadKey`. Telegram has no idempotency key, so delivery is at least once: `deliverMessage` locks the delivery row and only a crash between Telegram's 200 and our commit re-sends (stated in §8).
- Capabilities `{ streaming: false, maxLength: 4096, richContent: false, attachments: false, typing: false, footer: 'with_disclosure' }`. The new `footer` capability (`'every' | 'with_disclosure'`, default `every`) lets `shape.ts` put the GOV-14 privacy line only on the message that carries the AI disclosure (AGT-11), the first AI message in a chat, instead of under every chat bubble (D7). Cards are dropped and their text sent, as for email (FEAT-036 D7).
- Registry entry: `{ kind: 'telegram', name: 'Telegram', adapter, checksHealth: true, offlineModes: ['hidden', 'message'], connectPath: '/settings/channels/telegram', hook: 'telegram' }`; `ai_reply_cap` null (bots can't message bots, so there's no loop to cap; a tenant can't set one in FEAT-037).

### 5.2 Connect, replace, disconnect (`telegram/settings.ts`, API in the dashboard zone)

- **Connect:** token format → `getMe` (401/404 → `token_rejected`; network → `provider_unavailable`) → one transaction: `channel_connections` row (`telegram`, offline, `hidden`, credential = sealed JSON `{ token, webhookSecret }` with `webhookSecret` 32 random bytes base64url) and `telegram_settings` (bot id, username, name, secret hash; a unique violation on `bot_id` → `bot_in_use`) and audit `channel.connected` (kind, bot ID); after commit `setWebhook(PUBLIC_HOOKS_URL/hooks/telegram/<connection id>)`. A failed `setWebhook` leaves the channel connected and degraded `unreachable`, and the page's "Check again" re-registers it (the health check calls `setWebhook` when the URL is empty, never when it's someone else's).
- **Replace token:** `getMe` must return the stored `bot_id` (else 422 `different_bot`); seal the new credential with a new webhook secret, `version + 1`, audit `channel.token_replaced`, `setWebhook`, then `checkChannelNow` so a degraded channel recovers at once.
- **Disconnect:** offline, credential null, `telegram_settings` and every `telegram_alert_links` row deleted, `deleteWebhook`, audit `channel.disconnected`. `telegram_chats` stay, so reconnecting the same bot continues the chats; connecting a different bot after a disconnect deletes them first (its chat IDs mean nothing to the new bot).

### 5.3 Inbound (`telegram/receive.ts`, run by the api's hook route)

1. `channel_hook_route(connectionId, 'telegram')` → tenant and secret hash; none → 404. `verifyInbound`: constant-time compare of sha256(header) with the hash, else 401 (logged, nothing stored).
2. One visitor-zone transaction under `withTenant`, `pg_advisory_xact_lock` on the chat ID (two updates of one chat never race): insert `inbound_events` with `provider_event_id` = `update_id` (conflict → already handled, return 200). Then, first match wins:
   - **Link code:** a private `/start <payload>` whose sha256 matches an unexpired `telegram_alert_links.code_hash` → set `chat_id`, `telegram_name`, `linked_at`, clear the code; a service reply "You'll get {business} alerts here. Change them in KakiAgent: {app}/account/notifications" (outcome `accepted`, no conversation). An expired or unknown code → "This link has expired. Get a new one in KakiAgent." `/start` + anything that isn't a code is treated as plain `/start`.
   - **Group** (`group` or added to one) → `ignored`/`group`; once per chat, a service reply "I only answer private messages. Message me here: https://t.me/{bot}" and `leaveChat` (CHN-05; D2).
   - **A linked member's chat** (`chat_id` in `telegram_alert_links`) → `ignored`/`staff_chat` with the service reply "This chat gets your {business} alerts. To answer customers, use the inbox: {app}/inbox" (at most once an hour). `/stop` there unlinks.
   - **Blocked/unblocked** (`my_chat_member` in a private chat) → `telegram_chats.blocked_at` set or cleared, nothing else.
   - **Plain `/start`** with no conversation open: a service reply with the tenant's greeting (assistant settings, the language from `language_code`), the AI disclosure and the privacy line; no conversation yet (a tap on Start isn't a question).
   - **Unsupported** → the message is stored for staff as "[{kind}]" (e.g. "[Sticker]", "[Voice message]") with no turn, and a `text_only` system notice "I can only read text messages. Please type your question." at most once per conversation per 24 hours (delivered by the trigger like any message).
   - **Accepted text**: contact by `telegram_id` (insert with `name` = first + last name and `telegram_username`, D5); conversation = `telegram_chats.conversation_id` if it is open or reopenable (INB-08, 7 days), else `createConversation(tx, tenant, visitorId, 'telegram')` with `visitorId` = UUIDv5 of `tenant:telegram:<user id>` and `setConversationContact`; `appendVisitorMessage` with `clientMessageId` = `tg:<update_id>` (masking GOV-04, the turn job); upsert `telegram_chats`; `last_received_at`.
3. Service replies (not conversation messages) go through the outbox in the same transaction as a `channel-send` job `{ type: 'service', tenantId, connectionId, chatId, text, leave? }` (group = `tg:<chatId>`); the agent-worker's `channel-send` consumer sends it with the adapter and drops it after 24 hours of transient failures (nothing for staff to retry). Inbound idempotency is `inbound_events`; a 5xx before commit lets Telegram redeliver.
4. `InboxPort` (FEAT-036's `EmailInboxPort`, renamed and with `channel: 'email' | 'telegram'`) is passed by the api, which has inbox; channels still never imports inbox.

### 5.4 Outbound

Nothing new in the path: every message the agent, staff, notices or approvals write in a Telegram conversation already gets a delivery from the trigger, and `deliverMessage` calls the Telegram `ChannelSender` (chat ID from `telegram_chats` by conversation). New: `permanent` with `blocked` → `failed`/`blocked` and the `delivery_failed` escalation (staff see "The customer blocked the bot"; Retry stays possible after an unblock). The inbox's delivery line, Retry route and 24-hour timeout are FEAT-036's.

### 5.5 Alerts on Telegram (`platform/notifications`, `channels/telegram/alerts.ts`)

- `notify` writes one row per recipient **per channel** in `CHANNELS` (`email`, `telegram`), so each channel has its own status, retries and digest (D8). Producers don't change.
- `sendDueNotifications(idDb, mailer, opts)` gains `opts.telegram?: TelegramAlertSender` (`send({ tenantId, userId, text }) → 'sent' | 'no_channel' | { failed: 'transient' | 'auth' }`). For a `telegram` row: muted by `telegram_muted`, quiet hours and digests exactly as email (one digest message per member, business and channel); `no_channel` (no linked chat, or no bot) → `skipped`/`no_channel`; `transient`/`auth` → the existing backoff and 24-hour give-up. Without the port (tests, a role without it) telegram rows are `no_channel`.
- The scheduler binds the port to channels' `telegramAlerts(visitorDb, sealer, api)`: in its own visitor-zone transaction it reads the link and the sealed credential, sends, and on `blocked` deletes the link (the member blocked the bot: they stop getting Telegram alerts, the page shows "Not linked") and returns `no_channel`; on `auth` it calls `reportSendFailure` (degraded) and returns `auth`. Platform never imports channels; the identity zone never sees a bot token (D9).
- Text: `templates.ts` gets `alertText(item, ctx)` and `digestText(items, ctx)`, the email's plain-text body without the email furniture: "{business}: A customer asked for a person. Open: {link}" and a digest list; ≤ 4,096.
- **Degraded alert (CHN-12):** `recordHealth`, on the `degraded` transition, calls `notify` with kind `channel_degraded`, subject `channel`/connection ID, recipients = active members with `settings.manage`, dedupe key `channel_degraded:<connection>:<degraded_since>`, not urgent; on `recovered` it cancels them. The link is `/settings/channels`. Telegram's own degradation still reaches people by email (its telegram rows fail and give up).
- Test alert: also sent to Telegram when linked (`TestAlertResult.telegram`).
- Prefs: `savePrefs` sets `telegram_muted` from `EventPref.telegram` when present; `GET` lists `telegram` in `channels` when the tenant has a bot (connected, any state), with `sendTo.telegram` from the member's link (`pending` while an unexpired code exists).

## 6. Acceptance criteria

- **AC-1 (CHN-05 connect, UC-25 1–3, 3a):** An Owner or Admin pastes a valid token: the connection is created offline (hidden), the bot's name and @username show, the webhook is registered with a secret, and the token is stored only sealed; a malformed token, a token Telegram rejects, and a bot already connected to tenant B each give their 4xx with nothing stored; an Agent gets 403; tenant B can't read or change it.
- **AC-2 (CHN-05 "messages flow both ways"):** With the channel live, a private message creates a Telegram conversation linked to a contact with the Telegram ID and username, the AI reply is sent to that chat (with the disclosure and the privacy line on the first AI message only), a second message joins the same conversation, a staff reply from the inbox is sent through the bot, and a redelivered update creates nothing.
- **AC-3 (CHN-05 "group chats are ignored and the bot replies that it works only in private chats"):** A message in a group or supergroup, and the bot being added to a group, get no conversation and no AI reply; the bot sends the private-chats-only message once and leaves the group; the page counts it as ignored (group).
- **AC-4 (CHN-05 edge cases):** A sticker or voice message is shown to staff as "[Sticker]"/"[Voice message]" with no AI turn and one "text only" notice per 24 hours; a plain `/start` gets the greeting with the disclosure and creates no conversation; a customer who blocked the bot makes the next delivery `failed`/`blocked` with a `delivery_failed` escalation; NRIC in a message is masked.
- **AC-5 (CHN-12, UC-25 4a, NFR-17):** A revoked token is detected by the health check (401) and by a send (401) and marks the channel degraded; a webhook pointed elsewhere is `credential_invalid`; Owners and Admins get one `channel_degraded` alert by email (and Telegram when linked and the bot works), cancelled on recovery; replacing the token with one for the same bot recovers it at once, a different bot is 422; transient send failures retry and time out after 24 hours as for email.
- **AC-6 (LED-04 Telegram, DSH-09):** A member taps "Link Telegram", opens the `t.me` link and presses Start: their page shows "Linked"; an escalation alert then arrives on Telegram and by email; turning Telegram off for that event stops only the Telegram one; quiet hours hold both and the digest arrives on both; an urgent alert bypasses quiet hours on both; an expired code links nothing; the member blocking the bot unlinks them; Unlink stops Telegram alerts; a business without a bot shows no Telegram column.
- **AC-7 (ADR-005, ADR-014, ADR-015):** A wrong or missing secret header is 401 with nothing stored; `inbound_events`, delivery, outbox service rows and audit rows hold no message text or name; the bot token never appears in logs, the audit log or API responses; every new table passes the cross-tenant suite; a member can't read another member's alert link.
- **AC-8 (SCR-APP-039, SCR-APP-056, SCR-APP-014):** The Telegram page shows not connected, connecting, each token error, connected (offline and live), degraded (revoked, elsewhere) and disconnect; Notifications shows the Telegram column and the link states; the inbox filters by Telegram and shows the glyph, @username and the blocked delivery reason; no serious axe violations at 375 and 1280.

## 7. Decisions

- **D1 — Alerts come from the business's own bot** (recommended to Ken on a decision card, 2026-11-09; the design proceeds on it). Each member links their Telegram account to the bot the business connected, by a one-time `t.me/<bot>?start=<code>` link (15 minutes, hashed at rest). It needs no platform bot, keeps Telegram a recipient at the tenant's instruction (ADR-019), and puts alerts where SCR-APP-039 and UC-25 step 4 put them. *Cost:* a business without a Telegram channel gets email alerts only. *Rejected:* one KakiAgent alerts bot (makes Telegram a platform sub-processor; needs an ADR).
- **D2 — Groups: say it once, then leave.** CHN-05 asks for a reply in groups; answering every group message would spam the group, so the bot replies once and calls `leaveChat`. The page suggests turning off "Allow Groups" in BotFather (`/setjoingroups`), which only BotFather can do.
- **D3 — Webhook secret by hash.** Telegram echoes `secret_token` on every webhook; we compare its sha256 with `telegram_settings.webhook_secret_hash`, so receiving never unseals a credential (no KMS call per message). The secret also sits sealed with the token, so a token replacement can rotate both.
- **D4 — Connected offline and silent.** As for email (FEAT-036 D3): setup creates the channel offline with mode `hidden`, so nobody's messages are auto-answered before go-live; going live is FEAT-034's Channels action through `goLiveOne` (readiness unchanged).
- **D5 — Contact by Telegram ID.** `contacts` gains `telegram_id` and `telegram_username`; one Telegram user is one contact per business. It never merges with an email or phone contact automatically (CHN-08: "no automatic merge on unverified data"); verified and manual merges are FEAT-039's.
- **D6 — One bot per business, one business per bot.** `bot_id` is unique across tenants (a bot's webhook can point to one place only); a replacement token must be for the same bot, and a webhook someone else set is reported, never overwritten by the health job.
- **D7 — Privacy line once per chat.** GOV-14's link goes on the first AI message with the AI disclosure (and in the `/start` greeting), through a new `footer` capability; email keeps a footer on every message.
- **D8 — One alert row per channel.** `notify` writes an email and a Telegram row per recipient, so each has its own mute, retry and digest, and a Telegram failure never delays or duplicates the email. A Telegram row for someone without a link is skipped as `no_channel` at send time, so producers need no zone grants on the link table.
- **D9 — The bot token stays out of the identity zone.** The alert sender runs in the identity zone (FEAT-052 D10); Telegram sends go through a port the scheduler binds to channels, which reads the link and credential in the visitor zone.
- **D10 — Receive in the webhook's transaction.** ADR-011's flow persists the event before answering the provider; FEAT-037 also does the conversation work in that transaction (a few inserts, well within Telegram's timeout) and queues only the agent turn (`conversation-turns`) and service replies (`channel-send`), so no `telegram-inbound` queue is added. *Revisit:* if webhook latency grows past ~1 s.
- **D11 — Text only.** Photos, documents and voice aren't stored or read in FEAT-037 (CHN-09 attachments are widget-only and Should); staff see a placeholder. Inline-keyboard cards (consent, withdraw) are a follow-up (pending actions, FEAT-051).
